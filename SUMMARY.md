# richardbot-template — at a glance

A five-paragraph framing of two approaches to AI-context provisioning in a codebase, and a single chart that captures the structural differences.

---

Both approaches solve the same problem: a codebase is too large for any AI tool to learn organically inside a single conversation, and naive solutions (no context, or all-context-always) produce shallow exploration on one side and context-window exhaustion on the other. The question is what shape of context to provide and when.

The first approach — a single architecture-overview document, on the order of 500 lines, loaded into every conversation as `CLAUDE.md` or `.github/copilot-instructions.md` — is straightforward and effective for human readers. One file captures the entire codebase: tech stack, directory structure, every feature surface, build pipeline, framework architecture, styling, templating, integrations, analytics, naming conventions. There is no "do I have the right fragment loaded?" question because everything is always loaded. Authorial coherence is preserved; cross-references between sections are always in reach. No tooling is required beyond a markdown file at a known path.

The second approach — lazy-loaded fragments with agent-writable memory — splits the same content into small fragments (~50-80 lines each) under `.claude/rules/`, with YAML frontmatter declaring when each fragment fires. A hook at the AI's `UserPromptSubmit` event scans the frontmatter and loads only the slice matching the current prompt. Three content kinds coexist: human-authored rules (durable conventions), agent-writable memory (bug findings and friction observations regenerated by periodic scans), and a generated mirror that translates the corpus into the format GitHub Copilot reads. Runtime hooks gate destructive commands. Role files declare per-role model assignment (haiku for scans, sonnet for tests, opus for design) so subprocess dispatch is cost-explicit.

The two shapes optimize for different properties. The monolithic document wins on single-read discoverability, operational simplicity, and authorial coherence. It loses on per-turn context cost (fixed regardless of question scope), drift bound by human edit cadence, single-consumer lock-in, and the inability to retain bug findings discovered mid-conversation. The fragment approach wins on proportional per-turn cost (narrow prompts load narrow context), agent-writable memory that compounds across weeks of operation, periodic refresh via a `rescan` command that regenerates findings against the current codebase, multi-consumer mirroring (the same canonical source reaches Claude Code, Copilot, and any future tool with its own mirror), and runtime gates that move conventions from advisory text into mechanical enforcement. It loses on single-read discoverability, has a tooling dependency (a hook-honoring AI surface), and pays a higher operational surface area (multiple directories, a manifest, an archive).

The two are not mutually exclusive, and the hybrid is the most common steady state for teams adopting fragments in repos that already have a strong overview: install the monolithic document as a fragment with `alwaysApply: true` and layer per-surface fragments, memory, and mirror on top. The overview keeps its single-read coherence; fragments add lazy specificity; memory adds findings persistence; the mirror adds reach. This is the install shape produced by `richardbot-init init --full --overview <existing.md>` — one command, ~$3-5 of LLM subprocess cost, ~five minutes wall time, and the resulting state has both the human-readable narrative and the trigger-loaded specificity in the same repo.

## Chart — dimensional comparison

| Dimension | Monolithic document | Lazy-loaded fragments + memory |
|---|---|---|
| Loading model | Always-loaded | Trigger-based + always-on subset |
| Per-turn context cost | Fixed (~6K tokens) | Variable (200-2500 typical) |
| Source-of-truth shape | One file | One file per concept |
| Single-document read | Yes | Indirect (via `survey` command) |
| Agent-writable findings | No | Yes (`.richardbot-memory/`) |
| Refresh mechanism | Manual edit | `rescan` command, scriptable |
| Drift bound by | Human edit cadence | Scan cadence (cron-driven) |
| Cross-consumer | Per-tool copy | Single source, mirrored |
| Runtime tool gating | None | PreToolUse hooks |
| Model-explicit dispatch | Operator-handled | Role-file frontmatter |
| Cold-start cost | Author-time only | Author or LLM-generated |
| Operational surface | One file | Multiple dirs + hook + manifest |
| Failure under drift | Silent staleness | Archived stale + current memos side-by-side |
| Audit trail | Git blame | Git blame + `.archive/` history |

## Install (the hybrid)

```bash
# Skeleton only — directories, hooks, settings, baseline rules
richardbot-init init /path/to/repo

# Full autopopulate — skeleton + stack pack + per-surface fragments
# + import existing overview into fragments + bug-finding memory + Copilot mirror
richardbot-init init /path/to/repo \
  --full \
  --pack shopify-theme \
  --overview /path/to/existing-CLAUDE.md
```

The full command takes ~5 minutes wall time and ~$3-5 in LLM subprocess cost on a medium-sized repo. Produces a working install with concrete bug findings already planted in memory and ready to surface on the next prompt.
