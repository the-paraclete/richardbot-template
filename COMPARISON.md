# Two architectural shapes for AI-context provisioning

Two approaches to giving AI tools (Claude Code, Copilot, Cursor) the context they need inside a real codebase. Same problem; different shapes.

---

## Shape A — Single-document architecture overview

A ~500-line markdown file capturing the codebase as one structured reference: overview, structure, feature inventory, build pipeline, framework, styling, templating, integrations, analytics, i18n, dev workflow, deployment, naming conventions. Consumed as always-loaded context on every conversation.

**Strengths.**
- One source of truth; one read for full breadth.
- Authorial coherence — unified voice, consistent terminology, cross-references in reach.
- No tooling required.
- Naming and architectural conventions captured in the place engineers look.

**Structurally cannot do.**
- **Fixed per-turn cost.** Whole document loads whether the prompt is "build command?" or a whole-system question.
- **Drift.** Accurate at moment T; invisible to code added after T unless re-edited.
- **Single consumer.** A `CLAUDE.md` isn't a `.github/copilot-instructions.md`; each tool needs its own copy and they drift apart.
- **No agent-writable surface.** Findings discovered mid-conversation evaporate when the chat closes.
- **No runtime gating.** A doc is advisory; it can't block `git push --force`.
- **No model dispatch.** Doesn't influence how AI subprocesses are invoked.

---

## Shape B — Lazy-loaded fragments + agent-writable memory

A directory of small fragments (~50-80 lines each) with YAML frontmatter declaring when each fires. A UserPromptSubmit hook scans frontmatter and loads only the matching slice.

Three content kinds:

1. **Rules** (`.claude/rules/*.md`) — human-authored, durable: conventions, surface contracts, accessibility, error handling.
2. **Memory** (`.richardbot-memory/*.md`) — agent-writable: bug findings, friction notes, runbooks. Generated by periodic scans.
3. **Mirror** (`.github/copilot-instructions.md` + `.github/instructions/*.instructions.md`) — generated. Same corpus, second consumer.

Frontmatter triggers: `alwaysApply: true`, `triggers.prompt: [tokens]`, `globs: [patterns]`.

Typical turn loads 3-6 fragments (200-1200 tokens) out of a 1500-3000 line total corpus.

**Strengths.**
- **Proportional cost.** Narrow prompt loads narrow context.
- **Agent-writable memory.** Bug findings written to `.richardbot-memory/<surface>-bugs-YYYY-MM-DD.md` with file:line citations. Next conversation answers from memory, not by re-grepping.
- **Periodic refresh.** A `rescan` command re-runs scans on a schedule. Prior memos move to `.archive/` — audit trail preserved.
- **Multi-consumer mirror.** Same source, Copilot + Claude Code + (extensible) Cursor.
- **Runtime hooks.** PreToolUse gates block destructive patterns before they execute.
- **Model-explicit dispatch.** Role files declare haiku/sonnet/opus. Scans on haiku (~$0.05); tests on sonnet (~$0.20); design on opus (~$1+).
- **Composable.** Coexists with a monolithic overview as `alwaysApply: true`.

**Gives up.**
- **Single-read discoverability.** Breadth recoverable via `survey`, but not the default presentation.
- **Tooling dependency.** Needs `jq`, Bash, a hook-honoring AI surface. Copilot mirror is the fallback where hooks don't fire.
- **Cold-start cost.** Empty repo has no advantage; populating costs ~30 min author time or ~$3-10 LLM-generated.
- **Operational surface.** Three directories, a hook, a manifest, an archive. Each piece small; cognitive surface larger than one file.
- **Non-deterministic findings.** A bug present in week 1 may be absent in week 4 — fixed (good) or missed (noise). Archive preserves trail; operator reads both.

## Dimensional comparison

| Dimension | Shape A | Shape B |
|---|---|---|
| Loading model | Always-loaded | Trigger-based + always-on subset |
| Per-turn context cost | Fixed (~6K tokens) | Variable (200-2500 typical) |
| Source-of-truth shape | One file | One file per concept |
| Single-document read | Yes | Indirect (via `survey`) |
| Agent-writable findings | No | Yes |
| Refresh mechanism | Manual edit | `rescan`, scriptable |
| Drift bound by | Edit cadence | Scan cadence |
| Cross-consumer | Per-tool copy | Single source, mirrored |
| Runtime tool gating | None | PreToolUse hooks |
| Model dispatch | Operator-handled | Role-file frontmatter |
| Cold-start cost | Author-time only | Author or LLM-generated |
| Operational surface | One file | Multiple dirs + hook + manifest |
| Failure under drift | Silent staleness | Archived stale + current memos |
| Audit trail | Git blame | Git blame + `.archive/` history |

---

## The five axes that matter

**Per-turn cost.** Monolith pays fixed budget regardless of question scope. Fragments pay proportional. Cumulative dollar difference is modest; the real win is leaving more context window available for the work.

**Drift.** Documents capture moment T. Code added later is invisible until re-edited. Memory notes regenerate on schedule — drift bounded by scan cadence, not by who last had time to update a wiki.

**Multi-consumer.** Two parallel documents (one per tool) drift apart. A canonical source plus generated mirrors stays coherent. Adding a new AI tool means adding a new mirror, not a new manual sync.

**Runtime gating.** A documented "don't force-push" is advisory. A PreToolUse hook that blocks the command is mechanical. Different layer, different guarantee.

**Agent-writable findings.** The largest difference. In a monolith, an AI's bug-discovery dies with the conversation. In the fragment model, findings persist with frontmatter triggers — next time anyone asks about XSS in cart, the answer arrives with file:line citations, no grep required. The corpus compounds over weeks.

## Composability

Not mutually exclusive. Recommended hybrid for repos with an existing overview:

1. Move the overview to `.claude/rules/architecture-overview.md` with `alwaysApply: true`.
2. `richardbot-init init` — adds hook, memory directory, mirror tooling.
3. `richardbot-init survey` then `seed --surface <path> --write` for each surface — per-surface fragments with derived triggers and globs.
4. `richardbot-init rescan` — populate memory with concrete findings.
5. `richardbot-init copilot-mirror` — translate corpus to Copilot's format.

The overview keeps its discoverability; fragments add lazy specificity; memory adds persistence; mirror adds reach.

### What loads when

```
prompt: "what's the build command"
        ↓
   alwaysApply (5): accessibility, code-quality, conventions, es6-vue3, …
   matched by "build": architecture-build-pipeline, architecture-development-workflow
        ↓
   Loaded: 7 fragments, ~600 lines, ~2400 tokens
   Unloaded: everything else (~30 fragments, ~2400 lines, ~10000 tokens)


prompt: "is there an XSS risk in the cart"
        ↓
   alwaysApply (5)
   matched by "XSS": memory/cart-bugs-discovered-on-install
   matched by "cart": surface-vue-components-cart, shopify-cart-api, error-handling
        ↓
   Loaded: 9 fragments, ~900 lines, ~3600 tokens (with concrete file:line citations)
   Unloaded: everything else


prompt: "how does analytics route through GTM and Adobe"
        ↓
   alwaysApply (5)
   matched by "analytics" / "gtm": architecture-analytics-tracking,
                                   surface-vue-components-tracking
        ↓
   Loaded: 7 fragments, ~700 lines, ~2800 tokens
```

Shape A pays ~6000 tokens for context every turn regardless of prompt. Shape B pays 2000-4000 typical, never loads the parts of the corpus that aren't relevant to the question.

## Selection

**Shape A** when: stable codebase, single AI surface, operational simplicity outweighs cost variability, primary consumer is humans reading once.

**Shape B** when: active churn, multiple AI surfaces, runtime gating wanted alongside context, accumulating findings matters, subprocess cost control is a workflow concern.

**Hybrid** when: a strong overview already exists and the team wants both single-read coherence and lazy-loaded specificity. Most common steady state.
